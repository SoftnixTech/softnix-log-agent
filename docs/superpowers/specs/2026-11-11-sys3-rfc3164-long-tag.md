# SYS-3: RFC 3164 parser rejects `TAG[PID]` longer than 48 characters — design spec

Status: **decided 2026-11-11: option A** (relax the parser). Open
questions 2 and 3 keep their proposed answers unless the owner says
otherwise. Nothing is implemented yet.
Issue: SYS-3 in `ISSUES.md` (Low in `ISSUES.md`; this spec proposes
**Medium**, see Impact).
Branch: `develop_fix_bug_known-issues`.

## Problem

`parse_rfc3164` (`src/pipeline/syslog.rs:125`) accepts a tag only when
(`:166`):

```rust
if !tag.contains(' ') && tag.len() <= 48 {
```

`tag` is everything before the first `:`, **including the `[pid]`
suffix**. When the check fails, `application` and `process_id` stay
`None`, and the whole `TAG[PID]: msg` ends up in `message`. 48 is RFC
5424's APP-NAME limit. RFC 3164 §4.1.3 says 32 for TAG, but neither this
parser nor the agent's sender enforces that, and real Windows provider
names go well past both.

### New finding: real provider names fail even without spaces

`ISSUES.md` links SYS-3 to the provider-name fix, where spaces in names
are replaced by `_`. But the limit also hits names that **contain no
spaces at all**, on `main` and on this branch today. With a 4-digit PID:

| Provider | Name | `TAG[PID]` | Parsed? |
| --- | --- | --- | --- |
| `Microsoft-Windows-Security-Auditing` | 35 | 41 | ✅ |
| `Microsoft-Windows-PowerShell` | 28 | 34 | ✅ |
| `Microsoft-Windows-TerminalServices-LocalSessionManager` (RDP logon / logoff / reconnect, 21/23/24/25) | 54 | 60 | ❌ |
| `Microsoft-Windows-TerminalServices-RemoteConnectionManager` (RDP authentication, 1149) | 58 | 64 | ❌ |
| `Microsoft-Windows-DeviceManagement-Enterprise-Diagnostics-Provider` | 66 | 72 | ❌ |
| `Microsoft-Windows-Windows_Firewall_With_Advanced_Security` (after the provider-name fix) | 57 | 63 | ❌ |

### Evidence (2026-11-11, branch HEAD after `a508a6d`, 3 independent runs)

The harness (`issues_repro.py`, SYS-3 case) sends RFC 3164 lines to agent
B. The cut-off is exactly at 48. Every run was identical:

| Case | `TAG[PID]` length | `application` |
| --- | --- | --- |
| tagpid-47 / tagpid-48 | 47 / 48 | parsed ✅ |
| tagpid-49 / tagpid-50 | 49 / 50 | `None` ❌ |
| tag-nopid-48 / tag-nopid-49 | 48 / 49 | parsed ✅ / `None` ❌ |
| real-security-auditing (PID `720`, 3 digits) | 40 | parsed ✅ |
| real-firewall | 63 | `None` ❌ |

## Impact

**Medium** (up from Low). Only when the agent receives RFC 3164 (as a relay,
or from another agent with `format: rfc3164`), but the events that lose
`application` and `process_id` include **RDP logon tracking**
(TerminalServices-LocalSessionManager / RemoteConnectionManager), which
SIEM rules key on by provider. The rest of the line is not lost: it moves
into `message`. The reason it is not High is that the event still arrives,
and a rule matching on `message` text still works.

## Goals

1. The agent's receiver accepts every `TAG[PID]` that the agent's own
   sender emits for real Windows providers, so the two agree on the limit.
2. Anything accepted today is parsed **identically**: tags up to 48,
   tags with or without a PID, empty tags, and the existing tests.
3. A line with no real tag is still left alone. A space before the first
   `:` still disqualifies it, and an upper bound stays, so a long token
   without spaces before a colon is not mistaken for a tag without limit.

## Non-goals

- Enforcing RFC 3164's 32-character limit, on either side.
- Changing what the sender emits (unless the owner chooses option B).
- Spaces in TAG: header sanitization, which belongs to the provider-name
  fix.

## Options (open question 1)

**A — relax the parser (recommended).** Measure the **name** (before `[`)
and the **PID** (inside `[…]`) separately:

```rust
const MAX_TAG_NAME: usize = 128;
const MAX_TAG_PID: usize = 128;
// tag has no ' ', name.len() <= MAX_TAG_NAME, pid.len() <= MAX_TAG_PID
```

128 is about twice the longest real provider name found (66), and it
matches the PID cap that the provider-name fix's sender uses (its ruling
R-4). The sender stays unchanged, and no data is lost.

**B — cap the sender's TAG** so that `TAG[PID]` is at most 48. This
truncates long provider names on the RFC 3164 wire, permanently. RFC 3164
has no structured data to carry the original name. With a 4-digit PID the
name is cut to 42 characters: `Microsoft-Windows-TerminalServices-LocalSe`,
`Microsoft-Windows-TerminalServices-RemoteC`,
`Microsoft-Windows-DeviceManagement-Enterpr`. These names still differ,
but only by the luck of where the cut falls. SIEM rules written against
the full provider names stop matching, and providers that share a
42-character prefix would collide. It also changes what **third-party**
receivers get, which A does not.

Recommendation: **A**. It is a receiver-only change, keeps every byte the
sender sends, and fixes the agent's own receiver, which is the only side
`ISSUES.md` found broken.

This spec designs **option A only**. If the owner chooses B, the Design,
Testing and Rollout sections below must be rewritten for the sender
(`src/outputs/format.rs`) before a plan is written.

## Design (option A)

In `parse_rfc3164`, replace the `:166` condition:

1. `let (name, pid) = match tag.find('[') { Some(br) => (&tag[..br], Some(tag[br + 1..].trim_end_matches(']'))), None => (tag, None) };`
   The PID is measured as it is stored, without its closing `]`.
2. Accept when `!tag.contains(' ') && name.len() <= MAX_TAG_NAME &&
   pid.is_none_or(|p| p.len() <= MAX_TAG_PID)`. (`is_none_or`, not
   `map_or(true, …)`, which clippy rejects under `-D warnings`. It is
   stable since Rust 1.82, below the 1.98 MSRV.)
3. The body is unchanged: the same assignment of `application` /
   `process_id` / `message`, and the same handling of an empty tag.

Docs: add to the `inputs.syslog` `format` row (`docs/CONFIGURATION.md:138`,
`CONFIGURATION.th.md:137`) a short note that the RFC 3164 TAG name and PID
are each accepted up to 128 characters. The provider-name branch adds a
separate RFC 3164 *output* note (its `CONFIGURATION.md:412`). When the two
branches merge, that note must say the same thing, as `ISSUES.md` asks.

## Testing

Unit tests in `src/pipeline/syslog.rs`'s `mod tests`:

| Test | Input `TAG[PID]` | Asserts | Before the fix |
| --- | --- | --- | --- |
| `rfc3164_long_tag_with_pid_is_parsed` | `AAAA…(43)[1234]` (49) | `application` is the 43 A's, `process_id == "1234"`, `message == "hello"` | fails |
| `rfc3164_rdp_provider_tag_is_parsed` | `Microsoft-Windows-TerminalServices-LocalSessionManager[1234]` (60) | the same, with the real name | fails |
| `rfc3164_long_tag_without_pid_is_parsed` | 49 B's | `application` is the 49 B's | fails |
| `rfc3164_tag_at_48_unchanged` | 48 chars, with and without a PID | as today | passes (guard) |
| `rfc3164_tag_name_over_limit_is_not_a_tag` | a 129-char name | `application == None`, `message` holds the whole tail (today's behaviour for a too-long tag) | passes (guard on the new bound) |
| `rfc3164_tag_name_at_limit_is_parsed` | a 128-char name, with `[1234]` | `application` is the 128-char name, `process_id == "1234"` | fails |
| `rfc3164_tag_pid_over_limit_is_not_a_tag` | `app[` + 129 digits + `]` | `application == None`, `message` holds the whole tail | passes (guard on the new bound) |
| `rfc3164_tag_with_space_is_not_a_tag` | `two words[1]: x` | unchanged: `application == None` | passes (guard) |

The existing `rfc3164_*` tests stay green.

End-to-end: the harness's SYS-3 case (3 runs). Expected: 8/8 correct
(today 4/8).

Gate: fmt, clippy `-D warnings`, test `-D warnings`, `+1.98 check`.

## Risks

- **A token without spaces, 49–128 characters long, before the first `:`**
  in a line that has no real tag is now taken as the tag. Today the same
  thing already happens for tokens of 48 or fewer characters, for example
  `https` in `https://…`. The extra window is small, and it applies only to
  RFC 3164 lines that are already unusual.
